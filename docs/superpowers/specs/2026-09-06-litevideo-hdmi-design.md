# LiteVideo HDMI support: design

Date: 2026-09-06. Status: draft v1, written autonomously; decisions the user has
not confirmed are listed in section 3 so they can be overturned cheaply.

## 1. Goal

Turn LiteVideo's DVI-grade HDMI transmitter and receiver into real HDMI cores:

1. decode and generate HDMI data islands (TERC4 coding, preambles, guard bands,
   packet headers, BCH ECC, InfoFrames, General Control Packets);
2. extract audio from a received HDMI stream and inject audio into a
   transmitted one (Audio Sample Packets, Audio Clock Regeneration, Audio
   InfoFrame);
3. support the HDMI pixel encodings and colour spaces (RGB 4:4:4, YCbCr 4:4:4,
   YCbCr 4:2:2, BT.601/BT.709, full/limited range) with conversion between
   them and correct AVI InfoFrame signalling;
4. raise documentation and testing to the level of the better maintained LiteX
   cores (LiteEth, LiteDRAM, LiteX's own `soc/cores/video.py`).

Everything is Migen in LiteX style, tested in simulation, then on the NeTV2
boards in the Welland lab, first with Vivado and then with the open-source
flows (Yosys synthesis into Vivado, then Yosys + nextpnr-xilinx / openXC7).

Out of scope for this iteration: HDCP, CEC, deep colour (30/36-bit), 4:2:0,
HBR/One-Bit/DST audio, 3D, DisplayPort. The packet layer is written so those
packet types can be added without changing the island encoder/decoder.

## 2. Context and findings

### 2.1 The fork

`mithro/litevideo` was 149 commits behind `enjoy-digital/litevideo` with no
local changes; it was fast-forwarded to upstream `41f3014` and pushed
(2026-09-06). Upstream is 5,511 lines of Migen: `input/` (Spartan-6 and
7-Series TMDS receiver with char/channel sync, a `DecodeTERC4` island-period
state machine from the NeTV2 work, resolution detection, YCbCr 4:2:2 or RGB
frame capture into LiteDRAM), `output/` (frame parameter initiator, timing
generator, LiteDRAM DMA reader, `raw`/`rgb`/`ycbcr422` modes, Spartan-6 and
7-Series OSERDES PHYs with a raw 10-bit token path), `csc/` (RGB to and from
YCbCr, 4:4:4 to and from 4:2:2, 16-bit float), `terminal/` and
`float_arithmetic/`. Tests are per-package `*_tb.py` scripts run through
Makefiles; there is no `test/` directory and no CI. The README says
"Unit tests are available in ./test/" but no such directory exists.

### 2.2 Prior art in the concurrent NeTV2 project

`~/github/AlphamaxMedia/netv2-fpga` (branch `modern`, LiteX 2026.04) vendored
litevideo's input pipeline and built an HDMI audio pair in
`netv2/gateware/video/audio/`: `AudioPacketParser` (taps `DecodeTERC4`'s
nibble streams, reassembles 32-character packets, serial BCH check),
`HDMIAudioExtract` (ASP to PCM FIFO, ACR N/CTS latch, Audio InfoFrame latch,
CSRs), `AudioIslandEncoder` (framed island serialiser), `AudioEmbedder`
(CSR-driven scheduler rotating ACR, InfoFrame, ASP), a free-running 720p/1080p
timing generator and a self-timed fractional-MMCM raw output PHY. A fabric
loopback (embedder tokens fed straight into the decoder, no pins) was loaded
on `rpi5-netv2` and recovered N/CTS exactly; PCM payload was silent only
because the console could not feed the FIFO fast enough. Its conventions
(header on channel 0 bit 2; subpacket k bit 2c on channel 1 bit k and bit
2c+1 on channel 2 bit k; bytes LSB first) match the specification and
`hdl-util/hdmi`.

**Finding (ECC polynomial).** That work computes the ECC with the LFSR mask
`0x8B`, which is the polynomial x⁸ + x⁷ + x⁶ + x⁴ + 1. The HDMI specification
says otherwise: "BCH(64,56) and BCH(32,24) are generated by the polynomial
G(x) shown in Figure 5-5. G(x)=1+x6+x7+x8 (127 count repetition cycle)"
(HDMI 1.3, section 5.2.3.5). The independent `hdl-util/hdmi` implementation
uses `next_ecc = (ecc >> 1) ^ ((ecc[0] ^ next_bch_bit) ? 8'b10000011 : 8'd0)`,
that is mask `0x83`, the bit reversal of `0xC1` = 1 + x⁶ + x⁷ + x⁸. The
netv2-fpga encoder and decoder agree with each other, so their round trip
passes, but a real sink would drop every packet and a real source's packets
would fail its check. LiteVideo will use the specification polynomial and
must confirm it against packets from a real source on hardware (section 9).
The netv2-fpga session has been told nothing yet; this finding will be
reported to the user, who owns both trees.

### 2.3 LiteX conventions to follow

LiteX 2026.04 `litex/soc/cores/video.py` defines `video_timing_layout`
(`hsync, vsync, de, hres, vres, hcount, vcount`) and `video_data_layout`
(`hsync, vsync, de, r, g, b`), a CSR-configurable `VideoTimingGenerator`,
`ColorBarsPattern`, `VideoFrameBuffer` (LiteDRAM DMA, rgb888/rgb565/...),
and DVI-only PHYs (`VideoS7HDMIPHY` with `VideoS7HDMI10to1Serializer`,
`TMDSEncoder` in `code_tmds.py`). None of them can emit or receive data
islands. LiteVideo's new cores expose those same stream layouts so a LiteX
design can swap `VideoS7HDMIPHY` for LiteVideo's HDMI PHY and gain islands and
audio without other changes. Code style follows those files: `LiteXModule`,
`stream.Endpoint`, `CSRStorage/CSRStatus` with `CSRField` descriptions,
section banner comments, `# # #` separating interface from implementation.
Repository layout follows LiteEth: `pyproject.toml` + `setup.py`, `test/`
with `test_*.py` runnable by `pytest`, `bench/` for board targets, `doc/`,
`.github/workflows/ci.yml`.

## 4. Architecture

```
litevideo/
  hdmi/                      protocol layer, PHY independent, pure Migen
    common.py               tokens (control, TERC4, guard bands), layouts, packet type codes
    bch.py                  serial BCH(32,24)/(64,56) LFSR step + Python reference
    model.py                Python golden model: packet builders/parsers, ECC, TERC4,
                            island serialiser, InfoFrame checksums, N/CTS tables
    period.py               HDMIPeriodDecoder: raw 3-channel tokens -> period
                            (control/video preamble/video/data preamble/island),
                            hsync/vsync/de, TERC4 nibbles
    island/
      decoder.py            DataIslandDecoder: period + nibbles -> packet stream
      encoder.py            DataIslandEncoder: packet stream -> framed TERC4 tokens
      framer.py             HDMIFramer: video_data_layout + packet stream -> raw tokens
                            (TMDS encode, video preamble + guard band, islands in
                            blanking, control periods, optional AVMUTE/GCP)
    infoframe.py            AVI, Audio, SPD, GCP generators from CSRs (checksum in gateware)
    audio/
      common.py             audio sample stream layout, IEC 60958 flags
      extract.py            AudioExtract: packets -> PCM stream + N/CTS + InfoFrame + CSRs
      embed.py              AudioEmbed: PCM stream + N/CTS + InfoFrame -> packets
      acr.py                ACRGenerator: N/CTS constant or measured (audio-clock counting)
      sources.py            PCM sources: CSR FIFO, LiteDRAM DMA ring, tone generator
    scheduler.py            PacketScheduler: arbitrates ACR/ASP/InfoFrames/GCP into islands
  csc/                      existing, plus colorimetry/range parameterisation and
    convert.py              PixelFormatConverter (rgb444/ycbcr444/ycbcr422, 601/709, range)
  output/hdmi/              existing PHYs; S7 gains an "hdmi" mode that takes the framer's tokens
  input/                    receiver: HDMIIn gains packet_source, video_data_layout source,
                            format detection from AVI InfoFrame
test/                       pytest unit tests
bench/netv2/                board targets and host scripts for the hardware tiers
doc/                        documentation
```

Data flow, transmitter:

```
LiteX VTG/framebuffer/pattern  --video_data_layout-->  PixelFormatConverter
   --video_data_layout-->  HDMIFramer  --raw c0/c1/c2-->  S7HDMIOutPHY(mode="raw")
PCM source --audio stream--> AudioEmbed --packets--> PacketScheduler --packets--> HDMIFramer
InfoFrame generators (AVI/Audio/SPD/GCP) --packets--> PacketScheduler
```

Data flow, receiver:

```
S7DataCapture x3 -> CharSync -> ChanSync -> HDMIPeriodDecoder
   -> video: SyncPolarity -> video_data_layout source (+ PixelFormatConverter) -> frame capture
   -> islands: DataIslandDecoder -> packet stream -> AudioExtract (PCM stream, N/CTS, InfoFrame CSRs)
                                                  -> InfoFrame capture (AVI: format, colorimetry, range)
```

Clocking: transmitter logic in `pix`, serialisers in `pix5x`; receiver in the
recovered `pix` family. All CSR crossings use `MultiReg`, `BusSynchronizer`
or async FIFOs; every module documents its domains.

## 5. Components

### 5.1 `hdmi/common.py`, `hdmi/bch.py`, `hdmi/model.py`

Constants with spec references: control tokens (DVI 1.0 §3.2; HDMI 1.3
§5.4.2), TERC4 table (§5.4.3), video and data island guard bands (Tables 5-5,
5-6), preambles (Table 5-2), packet types (Table 5-8), ACR (Tables 5-10,
5-11), ASP (Tables 5-12, 5-13), InfoFrame (Tables 5-14, 5-15), GCP (Tables
5-16, 5-17), AVI and Audio InfoFrames (CEA-861-D §6.4 Tables 7-12, §6.6
Tables 16-20). `bch.py` provides `bch_step(state, bit)` (Migen expression)
and `bch_ecc(bytes)` (Python). `model.py` builds and parses every supported
packet, serialises islands into `(c0,c1,c2)` token lists including multi-packet
islands, and computes N/CTS. The gateware is tested against the model bit for
bit; the model is tested against hand-checked vectors (spec examples where
they exist, hdl-util's behaviour otherwise).

### 5.2 `hdmi/period.py` (receiver)

Replaces the ad-hoc `DecodeTERC4` with a documented state machine over the
three decoded channels: detects control periods (7-transition tokens), video
preamble (CTL 0001) and data island preamble (CTL 0101), leading/trailing
guard bands, and produces `period` (enum), `de`, `hsync`, `vsync`, the three
TERC4 nibbles, and a `packet_char_index`. Keeps a DVI fallback (DE from
non-control tokens) selectable per CSR, as `DecodeTERC4` had. `DecodeTERC4`
stays as a thin compatibility wrapper for one release.

### 5.3 `hdmi/island/decoder.py`

Reassembles 32-character packets from the nibble streams, checks header and
four subpacket ECCs serially, and emits `island_packet_layout` with `ecc_ok`.
Counters: packets, ECC errors, islands. Handles multi-packet islands.

### 5.4 `hdmi/island/encoder.py` and `hdmi/island/framer.py`

`DataIslandEncoder` takes a packet stream and emits the 32 TERC4 characters
per packet with serial ECC generation, and can chain up to N packets in one
island (§5.2.3.2 limits: island length 32 to 576 characters... encoded as
1 to 18 packets). `HDMIFramer` owns the line: during blanking it emits control
tokens with hsync/vsync, inserts the data island preamble (8 characters),
leading guard band (2), packets, trailing guard band (2), then the video
preamble (8) and video guard band (2) before DE. It computes when an island
fits in the remaining blanking (§5.2.3.2 placement rules, including the
requirement that islands end at least 32... characters before video and the
minimum control period) and only accepts a packet from the scheduler when it
fits. TMDS encoding of active pixels reuses `output/hdmi/encoder.py`
(pipeline latency aligned with the framer). Output is the raw token stream.

### 5.5 `hdmi/infoframe.py`

AVI InfoFrame generator: Y (RGB/YCbCr444/YCbCr422), A, B, S, C (colorimetry),
M, R, EC, Q (RGB range), VIC, PR, YQ; checksum in gateware. Audio InfoFrame:
CC, CT, SF, SS, CA, LSV, DM_INH. SPD: vendor/product strings from a ROM.
GCP: AVMUTE set/clear, colour depth = 24-bit. Each produces a packet on
demand (per frame or on change) into the scheduler.

### 5.6 `hdmi/audio/`

`AudioExtract`: ASP to a PCM stream `[("sample", 24), ("channel", 3), ("v",1),
("u",1), ("c",1), ("p",1), ("b",1)]` honouring sample_present and layout;
ACR latch; Audio InfoFrame latch; counters; optional async FIFO to `sys`;
`sample_source` for DMA or CSR drain. `AudioEmbed`: PCM stream to ASPs
(2 samples per subpacket, layout 0; layout 1 for 3 to 8 channels), IEC 60958
B/V/U/C/P generation (channel status block of 192 frames, basic consumer
format), rate control so ASPs are only emitted when a full sample set is
queued (fixes the netv2-fpga behaviour that emits silence packets when the
FIFO is empty). `ACRGenerator`: constant N/CTS from the table for coherent
clocks, or measured CTS (count `pix` cycles per N/128 audio-clock cycles, HDMI
Figure 7-1). `sources.py`: CSR FIFO (bring-up), LiteDRAM DMA ring (host-fed),
`ToneGenerator` (fabric sine table at a chosen frequency; the hardware test
signal that needs no host bandwidth).

### 5.7 `hdmi/scheduler.py`

Round-robin with priorities: ACR (must meet §7.8.2 delivery), ASP (rate),
GCP (once per frame when muting/changing), AVI and Audio InfoFrames (once per
frame per CEA-861-D), SPD (every few frames). Emits at most one island per
blanking opportunity offered by the framer, packing several packets per island
when allowed.

### 5.8 `csc/convert.py` and colorimetry

Parameterise `RGB2YCbCr`/`YCbCr2RGB` coefficients for BT.601 and BT.709 and
full/limited range (Xilinx XAPP930 equations are already the basis). Add
`PixelFormatConverter(fmt_in, fmt_out)` over `video_data_layout` (YCbCr 4:2:2
carried as HDMI §6.5.1 Figure 6-x mapping: Y on the "g" channel, Cb/Cr
multiplexed on "r"/"b" with the 4 MSBs... encoded exactly as the wire format so
`rgb`-labelled channels carry whatever the AVI InfoFrame declares). Receiver:
the AVI InfoFrame (Y bits, C bits, Q bits) selects the converter to RGB for
frame capture; transmitter: a CSR selects the output format and the AVI
generator is driven from the same register.

### 5.9 Integration classes

`HDMIOut(pads, ...)`: `sink` (`video_data_layout`), `audio_sink`, CSRs for
format, InfoFrames, N/CTS, AVMUTE; owns the framer, scheduler, PHY. Keeps the
existing `VideoOut` (DMA-driven) working and adds an `hdmi=True` path.
`HDMIIn`: adds `packet_source`, `audio_source`, `video_source`
(`video_data_layout`), InfoFrame capture CSRs, keeps the DMA frame capture.

### 5.10 `bench/netv2/`

Targets (LiteX `LiteXArgumentParser` style, `--toolchain vivado|openxc7`):
`hdmi_loopback` (framer tokens into the receiver protocol layer inside the
fabric, tone generator into audio embed, audio extract read back, frame CRC),
`hdmi_tx` (self-timed 720p60 colour bars + tone + InfoFrames on `hdmi_out` 0),
`hdmi_rx` (receiver on `hdmi_in` 0 with island capture and audio drain),
`hdmi_txrx` (both, for the cabled loopback). Host scripts in Python (uv):
program via openFPGALoader over ssh, drive CSRs over the LiteX BIOS console or
Etherbone, assert results, write a report under `doc/reports/`.

## 6. Testing

Tier 0, simulation (`pytest test/`): `test_bch.py` (model vs known vectors,
gateware vs model over random data), `test_tokens.py` (TMDS encode/decode,
TERC4 encode/decode round trip, DC balance), `test_period.py` (state machine
over model-generated lines with random blanking), `test_island_decoder.py`
(single and multi-packet islands, corrupted ECC, back-to-back islands),
`test_island_encoder.py` (token stream byte-exact vs model), `test_framer.py`
(line timing preserved, guard bands and preambles placed per §5.2.3.2,
islands never overlap DE, minimum control periods kept),
`test_infoframe.py` (checksums, field placement vs CEA-861-D tables),
`test_audio_extract.py` / `test_audio_embed.py` / `test_audio_roundtrip.py`
(bit-exact PCM, N/CTS, layout 0 and 1, channel status block), `test_acr.py`
(measured CTS within 1 count), `test_scheduler.py` (delivery rates, no
starvation), `test_csc.py` (converters vs float model within 1 LSB, range
mapping), `test_hdmi_out.py` / `test_hdmi_in.py` (full transmitter into full
receiver in one simulation: video CRC and audio bit-exact). Existing csc test
benches are ported into `test/`.

Tier 1 to 4 as in D10, each with a script that produces a dated report with
the bitstream SHA-256, build timing/utilisation, console transcripts and the
pass/fail table (following netv2-fpga's `docs/testing/reports/` practice).

## 9. Hardware validation plan and what needs the user

| Tier | Needs | Proves |
|---|---|---|
| T1 fabric loopback on rpi5 | nothing new | framer, islands, ECC, audio round trip, InfoFrames on silicon at the pixel rate |
| T2 cabled loopback on rpi5 | **user plugs HDMI cable `hdmi_out` 0 → `hdmi_in` 0** | OSERDES/ISERDES, clock recovery, real TMDS with islands, both directions of the ECC against each other |
| T3 real source on rpi3 | **user releases rpi3 after HDCP work**; `rpiz-3` HDMI audio enabled | ECC polynomial and byte order against a real source (the decisive check for D6), AVI/Audio InfoFrame decode, audio extraction of a real tone |
| T4 real sink | **user reconnects the MS2109 (UVC+UAC) to rpi3's `hdmi_out` 0** or provides another audio-capable sink | transmitter accepted by a commercial sink: video lock, audio InfoFrame honoured, tone recovered from the capture card's ALSA device |

Without T3 or T4 the ECC choice rests on the specification text and
hdl-util; the report will say so.

## 11. Risks

- ECC/byte-order convention unverifiable without a real source (mitigation:
  spec text + hdl-util; T3/T4 when available; flag in docs).
- 1080p60 output SERDES (743.75 MHz) does not close on the -2 part (netv2-fpga
  measurement); default 720p60, 1080p documented as speed-grade limited.
- openXC7 receiver path blocked by nextpnr-xilinx ISERDESE2/MMCM issues;
  treated as a measured feasibility result, not a promise.
- Shared machine: memory pressure from Vivado (mitigated by the cgroup
  wrapper, one build at a time).
- The receiver's alt_delay path depends on three Verilog black boxes in the
  NeTV2 tree that are not in litevideo; litevideo's own aligner is used.
